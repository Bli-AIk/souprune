# Architecture

> For the Simplified Chinese version, see [architecture_zh-hans.md](architecture_zh-hans.md).

This document describes the current internal architecture of SoupRune.

---

## Big Picture

SoupRune is a generic framework on top of Bevy. The distributed binary contains
the framework runtime, host primitives, and schema/SDK contracts; game semantics
are authored in project content, project assets, and project WASM runtimes.

```
┌──────────────────────────────────────────────┐
│  Project Layer                                │
│  projects/<project>/                          │
│  RON generated by content crates, Mortar,      │
│  FRE rules, assets, and WASM runtime logic     │
├──────────────────────────────────────────────┤
│  Framework Layer                              │
│  crates/souprune/src/core/                    │
│  View, FRE bridge, Mortar integration,         │
│  danmaku, collision, input, mode registry,      │
│  host primitives, schema-backed content loading │
├──────────────────────────────────────────────┤
│  Schema and SDK Layer                          │
│  crates/souprune_schema, souprune_api,         │
│  souprune_sdk, cauld-ron tooling               │
└──────────────────────────────────────────────┘
```

The dependency direction is strict: framework code defines generic host
primitives and schemas; project content and project WASM runtimes compose those
primitives into a game. Framework Rust owns generic infrastructure; project-only
gameplay layers belong under `projects/<project>/`.

## Framework Runtime

`crates/souprune/src/core/` contains reusable infrastructure:

- `input/`: normalized input transactions and binding configuration.
- `view/`: RON-driven declarative UI, `LocalState`, SDF shapes, text, and
  reconciliation.
- `fre_bridge/`: routes input, view actions, collision, custom actions, and fact
  mutations between ECS and FRE.
- `sequencer/`: chapter-based flow control, `Custom` actions, `RunSequence`,
  `LoadMap`, dialogue and view chapters.
- `danmaku/`: bullet performances, timelines, builtin motion primitives, and
  WASM behavior integration points.
- `collision/`: host collision primitives exposed to project runtimes.
- `mod_system/`: WASM loading, behavior dispatch, custom action dispatch, host
  entity primitives, and audio side effects.
- `fixed_scene/`: fixed-camera scene primitive bundle for camera/input setup,
  sequencer/FRE wiring, and danmaku integration. It is not a built-in mode
  named `battle`.
- `top_down/`: top-down map primitive bundle for tilemaps, player movement,
  interaction zones, chase, and map-scoped FRE integration. Core may provide
  tilemaps and other high-frequency primitives; project configuration owns mode
  names and gameplay meaning.
- `content/`: schema-backed asset loading and fact projection for enemy/item
  data used by the current project formats.

Projects declare mode names, enabled primitives, entry sequences, FRE rules, and
fixed-camera parameters through `game.modes.<id>` in `mod.toml`. Names such as
`battle`, `overworld`, `field`, or `puzzle` are project data. Core does not
register those names by default and must not switch systems by matching them.

Some modules use current project-format terms such as item, enemy, or
battle. The boundary is not the word itself; the boundary is ownership.
Framework code may load typed data, project it into facts, and provide reusable
primitives. Project-specific rules such as item use effects, enemy turn
selection, battle boxes, and player spawn semantics must live in project content
or project WASM runtimes.

## Project Layer

`projects/<project>/` is the mod author surface.

| Surface | Owner | Purpose |
| --- | --- | --- |
| `content/src/**` | project content crate | Generates RON files through cauld-ron. |
| `.ron` artifacts | generated output | View layouts, sequences, rules, data assets. |
| `.mortar` | project scripts | Dialogue trees and scripted text. |
| `runtime/src/**` | project WASM runtime | Custom behaviors, custom actions, and gameplay semantics. |
| assets | project | Sprites, audio, tilemaps, and Alight Motion files. |

RON files under `projects/` are generated artifacts. Change the corresponding
content crate source, rebuild the content, and let cauld-ron emit the RON.

## Boundary Examples

Framework owns:

- `core::collision::region::CollisionRegion` and movement constraints.
- `core::mod_system` host entity primitives such as spawning a sprite or view
  box from WASM.
- `core::sequencer::Chapter::Custom` and custom action dispatch.
- tilemaps, fixed-camera scenes, top-down movement, and interaction-zone
  primitives.
- `ModeRegistry` checks project configuration to decide which primitives are
  active in the current mode.
- `core::content::enemy::EnemyDef` loading and projection into facts.

Project runtime owns:

- `SpawnBattleBox`, `SplitBattleBox`, and `MergeBattleBoxes` custom actions.
- `SpawnBattlePlayer` and red-soul behavior.
- `UseItem`, `CheckItem`, and `DropItem`.
- Enemy turn selection strategy.
- Boss-specific danmaku behaviors and patterns.

This split keeps the binary generic while projects ship rich behavior through
their own runtime modules.

## Core Systems

### FRE

FRE is the data-driven rule engine. Events trigger rules; rules mutate facts;
View and runtime systems react to those facts. FRE is a framework mechanism, not
a dumping ground for every gameplay behavior. When behavior belongs to a project,
FRE should dispatch a `Custom` action and let project WASM own the semantics.

### View

View layouts are declarative RON files. View owns its `LocalState`; external
systems read it through controlled snapshots and mutate it only through explicit
commands or scoped custom-action side effects. View-specific state must not be
hidden inside FRE as an implicit owner.

### Input

Input enters the framework through normalized input transactions. View, FRE, and
WASM behaviors consume the same transaction model, but each bridge decides how
to translate it into local commands. The input transaction carries the current
project-declared mode name rather than built-in `battle` / `overworld` contexts.
Raw direct key reads are not a long-term extension point.

### WASM Runtime

Project WASM runtimes are the extension point for custom behavior. They can read
and write facts, react to input envelopes, spawn host primitives, play audio, and
handle custom actions. Hot reusable primitives stay in Rust; project semantics
belong in WASM/content.

## Guardrails

Allowed in framework Rust:

- Generic rendering, input, audio, collision, danmaku, dialogue, View, FRE, and
  sequencer infrastructure.
- Typed schema-backed asset loading when the format is a framework-supported
  authoring surface.
- Generic host primitives exposed to WASM.

Forbidden in framework Rust:

- Project-specific gameplay layers inside framework crates.
- Alternate entrypoints outside the public schema/SDK surface.
- Project-only gameplay commands hardcoded into the binary.
- BattleBox/BattlePlayer gameplay abstractions in `core/`.
- Special item-use or enemy-turn behavior outside project runtime.

`scripts/check_core_boundaries.sh` and `crates/souprune/tests/architecture_boundaries.rs`
enforce the most important parts of this boundary.
